# 测试与运行观测系统需求

## 简介

测试与运行观测系统统一后端测试、前端测试、真实 HTTP 检查和 Playwright 巡检的执行口径与报告结构，并在 B 端提供受权限保护的运行看板。

## 术语

- **测试清单**：定义检查模块、执行器、标签和运行级别的结构化配置。
- **检查模块**：可独立运行的质量检查单元，例如后端单元测试、前端 Vitest、API 检查或页面巡检。
- **批量检查**：按照预定义范围组合执行多个检查模块。
- **运行报告**：一次检查执行产生的统一 JSON 结果，包含摘要和失败详情。
- **运行看板**：B 端用于查看系统状态、功能可用性和检查结果的页面。

## 需求

### 需求 1：统一测试编排

**用户故事：** 作为开发人员，我希望通过固定命令运行明确范围的检查，以便本地、CI 和部署前验证使用一致的质量标准。

#### 验收标准

1. 测试系统应从测试清单解析检查模块、标签和执行命令。
2. 当开发人员选择 `quick`、`full` 或单个检查模块时，测试系统应执行测试清单定义的目标集合。
3. 当检查模块失败时，测试系统应以非零退出码结束，并在运行报告中记录失败原因。
4. 当测试系统生成运行报告时，运行报告应包含执行标识、开始时间、结束时间、状态、摘要和检查结果。
5. 当测试系统执行后端分层测试时，测试系统应通过 pytest marker 或单一清单确定覆盖范围。

### 需求 2：统一结果报告

**用户故事：** 作为运营人员，我希望从统一报告查看检查状态和失败项，以便判断功能可用性。

#### 验收标准

1. 每次检查完成后，测试系统应输出包含 `timestamp`、`target`、`status`、`summary` 和 `results` 的 JSON 报告。
2. 运行报告摘要应包含总数、通过数、失败数、警告数、跳过数、通过率和耗时。
3. 每个检查结果应包含名称、状态、标签、耗时和可操作的失败详情。
4. 当检查产生原始测试报告时，测试系统应在统一报告中保留原始报告的位置。
5. 当系统重启后，运行看板应从已归档报告恢复最近一次完成的检查结果。

### 需求 3：自检执行能力

**用户故事：** 作为系统管理员，我希望服务启动时得到基础可用性状态，并能按模块或批量触发检查，以便快速定位运行问题。

#### 验收标准

1. 当自检服务启动时，自检服务应执行一次健康检查并保存结果。
2. 当管理员选择健康、API、页面、业务流或完整检查时，自检服务应创建异步检查任务并返回任务标识。
3. 当异步检查任务运行时，系统应提供任务状态、开始时间、结束时间和错误信息。
4. 当管理员选择批量检查时，系统应按预定义范围执行对应检查模块。
5. 当自检服务不可用时，运行看板应显示自检服务状态和恢复提示。

### 需求 4：运行看板

**用户故事：** 作为拥有系统配置权限的管理员，我希望查看系统状况、项目运行情况和功能可用性，并从页面发起检查。

#### 验收标准

1. 运行看板应提供独立 B 端路由和菜单入口。
2. 当管理员打开运行看板时，运行看板应显示自检服务状态、最近检查状态、通过率、失败数和耗时。
3. 运行看板应按健康、API、页面、业务流和性能维度显示功能可用性状态。
4. 当最近报告包含失败项时，运行看板应显示失败项名称、详情、标签和耗时。
5. 当管理员发起检查后，运行看板应轮询任务状态并在任务完成后刷新报告。
6. 运行看板应使用现有 `system.config` 权限控制页面访问和检查操作。

### 需求 5：CI 周期检查

**用户故事：** 作为项目维护者，我希望 CI 在代码变更和定期计划中执行关键检查，以便持续发现回归。

#### 验收标准

1. 当 pull request 或受保护分支发生变更时，CI 应执行与本地质量门禁一致的核心检查。
2. 当定时 CI 工作流触发时，CI 应启动测试依赖并执行关键真实请求检查。
3. 当 CI 检查失败时，CI 应以失败状态结束并保留运行报告作为构件。
4. 当 CI 检查完成时，CI 应发布可供后续分析的报告构件。

## 范围边界

- 定期执行由 CI 平台工作流触发。
- 浏览器仅访问 B 端 API；后端服务端访问自检服务。
- 看板展示当前实例的应用指标，并在界面标注该范围。
