# 后端三层架构

## 概述

后端采用经典的三层架构：API 路由层 → 服务层 → 仓储层，配合 ORM 模型层实现数据持久化。API 接口列表见 [INTERFACES.md](../INTERFACES.md)，核心概念见 [状态机](../专有概念/状态机.md)、[双Token鉴权](../专有概念/双Token鉴权.md)、[敏感词系统](../专有概念/敏感词系统.md)。

## 核心组件

### 配置管理

文件: `backend/app/core/config.py`

使用 `pydantic-settings` 的 `BaseSettings`，支持 `.env` 文件覆盖。关键配置：

- `db_url`: 数据库连接（默认 SQLite，生产用 MySQL）
- `redis_url`: Redis 连接
- `jwt_secret`: JWT 密钥
- `access_token_ttl`: Access Token 有效期（默认 8h）

### 数据库

文件: `backend/app/core/database.py`

- 异步引擎: `create_async_engine`
- 会话工厂: `AsyncSessionLocal`
- SQLite 默认（开发），MySQL 生产（asyncmy 驱动）
- 启动时自动 `create_all` 建表

### 异常体系

文件: `backend/app/core/exceptions.py`

```python
class BizError(Exception):
    def __init__(self, code: int, message: str, http_status: int = 200):
        self.code = code
        self.message = message
        self.http_status = http_status
```

### 缓存策略

- Redis 缓存发现页、书籍详情、排行榜等热点数据
- Cache-Aside 模式：先读缓存 → 未命中查数据库 → 写入缓存
- 开发/测试时 Redis 不可用自动降级为 fakeredis
- 缓存写入统一走 `utils/cache.cache_set`，TTL 带随机抖动（防缓存雪崩）
- 时间戳口径统一走 `utils/time.now_ms`（毫秒，1 秒缓存）

#### 缓存健壮性

- **防雪崩**：`cache_set` 对 TTL 施加 ±10% 随机抖动，避免批量缓存同时过期
- **防击穿**：重建成本高的热点 key（发现页聚合 `c:discovery:home`）走
  `utils/cache.cache_single_flight` 单飞锁，缓存失效瞬间仅一个请求回源，
  其余等待锁释放后复用缓存
- **防穿透**：书籍详情对不存在的作品写入短 TTL（60s）空值标记 `{"_miss": true}`，
  避免恶意请求反复回源；B 端状态/信息变更会失效该键，发布后可正常读取
- 空数据结构（如空排行榜）同样写入缓存，天然防穿透

#### 缓存键与失效映射

| 缓存键 | 写入点 | 读取点 | 失效点 |
|--------|--------|--------|--------|
| `c:discovery:home` | DiscoveryService | DiscoveryService | NovelService._evict_novel_caches |
| `c:book:{id}` | BookService._get_published_novel | BookService | NovelService 状态/编辑变更；InteractionService.submit_rating（评分） |
| `c:book:{id}:chapters` | BookService.get_chapters | BookService | ChapterService 增删改/排序/状态流转；NovelService 状态变更 |
| `c:book:{id}:rating` | BookService.get_rating_distribution | BookService | InteractionService.submit_rating |
| `c:chapter:{nid}:{cid}` | BookService._cache_chapter | BookService | ChapterService 编辑/删除/状态流转 |
| `c:rank:{type}` | DiscoveryService | DiscoveryService | NovelService 状态变更；评分（ticket 档） |
| `c:books:hot` / `free-limited` / `editor-picks` | DiscoveryService | DiscoveryService | NovelService 状态变更 |
| `c:categories` / `c:tags` | DiscoveryService | DiscoveryService | 静态数据（种子），无失效需求 |
| `c:recommend:hot` | RecommendService | RecommendService | TTL 600s 自然过期 |
| `c:search:sug:*` / `c:search:hot` / `c:pinyin:candidates` | SearchService | SearchService | TTL 自然过期 |
| `c:me:bookshelf:{rid}` / `c:me:follows:{rid}` | UserCenterService | UserCenterService | InteractionService 书架/追更变更 |
| `c:me:heatmap:{rid}` | UserCenterService.get_heatmap | UserCenterService | InteractionService 阅读进度落库 |
| `b:workbench:kpi` | WorkbenchService | WorkbenchService | TTL 300s 自然过期 |
| `auth:access:{token}` / `auth:refresh:{token}` | 鉴权服务 | deps 鉴权 | 登出/刷新/失效 |
| `c:book:click:{id}` | BookService._incr_click | DiscoveryService._flush_click_counts | 同步回 DB 后删除 |

> 维护约定：任何写操作若导致缓存数据的源数据变化，必须同步失效对应缓存键，
> 否则读者可能在 TTL 内读到过期数据。新增缓存键时更新本表。

## 数据流示例

以「获取书籍详情」为例：

```
GET /api/v1/c/books/123
    ↓
BookService.get_book(book_id=123, reader_id=1001)
    ↓
检查 Redis 缓存 → 命中则直接返回
    ↓
未命中 → NovelRepository.get_by_id(123)
    ↓
SQLAlchemy 查询 → ORM → 返回 Novel 模型
    ↓
_converters.novel_to_c_summary(novel, is_in_shelf)
    ↓
写入 Redis 缓存
    ↓
返回 BookSummary Schema
```

## 已知演进方向

- **分页**：offset 分页在中小数据量下索引覆盖良好（audit 走 `(status, submitted_at)`、chapter 走 `(novel_id, index)` 唯一索引）。数据量显著增长后需演进为 keyset（游标）分页，需前端配合改造。
- **幂等性**：评分/点赞/书架/阅读进度/敏感词写入均有唯一约束 + IntegrityError 兜底，天然幂等。
  打赏、评论、回复等非幂等写操作支持可选 `Idempotency-Key` 请求头（`utils/idempotency.idempotent_run`，
  SETNX 幂等键 + TTL 内重复键直接返回 `duplicate: true` + 执行失败自动释放重试）；客户端为每次提交
  意图生成唯一键（UUID），重试复用同一键即可防重复扣费/刷评论。不传该头则保持原行为。
- **RUM 表**：埋点数据量大，已为 `created_at` 建立索引；后续按 `type + created_at` 查询更频繁时可扩展复合索引，并考虑按天归档/分区。

### 契约与基准

- **Schema 契约测试**（`tests/test_schema_contract.py`）：遍历全部 `CamelModel`，
  断言序列化别名无下划线（camelCase），防止新增字段破坏前端契约
- **API 真实请求契约测试**（`tests/test_api_contract.py`）：遍历 OpenAPI 全部端点
  （GET 67 + 写端点 46），实际发请求验证统一响应体 `{code, message, data}` 结构。
  曾借此发现异常响应因 `exclude_none` 丢失 `data`/`traceId` 字段的契约 bug；写端点
  用空请求体触发参数校验路径验证契约
- **性能基准**（`tests/test_benchmarks.py`，`--benchmark-only` 运行）：协同过滤
  纯函数、推荐（冷启动/有历史）、搜索、敏感词 Trie 扫描、书架批量加载、去重算法
